# Region `Radius / Scale` Clarification（Phase 3.1.6 · 字段语义最小澄清）

> **文档性质**：**最小澄清核验（Minimal Clarification）**。只回答一个问题：`§3.2` 的 `Radius / Scale` 是**一个**概念字段，还是**两个独立**概念字段。
>
> **本轮边界（已遵守）**：不修改任何现有契约 / 审计报告 / 代码；不新增或修改 `.cs` / `.meta` / 测试 / 场景 / Prefab；不确定上限 A/B；不实现来源载体、来源生成或来源枚举；**不裁决** `RID57`–`RID63`；**不把 `Radius` 解释成搜索半径或影响半径**；**不把 `Scale` 解释成缩放因子**；不为了闭合设计而自行创造二者关系。
>
> **证据标准**：每条结论标 `【原文】`（可直接核对行号）或 `【推断】`（由原文推导，非契约声明）；无法判定者标 `【未判定】`。
>
> **一句话结论**：
> **`Radius / Scale` 在 §3.2 中占用了表格的"一个字段行"；三条下游条款（`RA34` / `RA39` / `RA51`）把它当作"一项"来处理，另有三处只写 `Radius`、`Region_Design` 用 `Size` 指同一量——因此"单字段"是**证据更强的读法**（推荐）；但**没有一条条款明文宣布"二者同义"**，故最终仍需设计者用最小澄清（§6）确认；该澄清**不需要**裁决任何空间语义（§7）。**

## §3 七问逐答

### Q1：`Radius / Scale` 是"一个字段标题 / 两个字段 / 尚未明确的候选表达"？

| 判定 | 内容 |
|---|---|
| **【原文】** | §3.2 的字段表（`L156`–`L165`）中，`Radius / Scale`**只占一行**（`L162`），该行只有**一个含义**（`影响尺度`）与**一组约束**（`世界单位；必须 > 0`） |
| **【原文】** | 同一张表中，斜杠并列的写法**还出现在** `Epoch / Ordinal`（`L163`）——而 `Epoch` 与 `Ordinal` 在别处**被分别对待**：`RA9`（`L125`）把它们分别列入 `RegionKey`，`RA11`（`L127`）分别给出约束 → **斜杠写法本身不构成"一个概念"的证明** |
| **【原文】** | 反方向证据：对 `Radius/Scale`，**没有任何条款**把它拆开分别约束或分别赋值；而 `Epoch`/`Ordinal` 有 |
| **【推断】** | 因此 Q1 的答案是：**它是一行"尚未明确"的并列表达**；"一个字段标题"是**形式事实**（占一行、一含义、一组约束），"是否代表一个概念"**未由该行本身决定** |

### Q2：是否存在足够证据证明 `Radius` 与 `Scale` **同义**？

| 证据 | 内容 | 类型 |
|---|---|---|
| **E-1** | §3.2 该行只有**一个含义**（"影响尺度"）与**一组约束** | 【原文】 |
| **E-2** | `RA34`（`L195`）把 **`Strength`、`Radius/Scale`** 并列为两项 → `Radius/Scale` 被当作**一项** | 【原文】 |
| **E-3** | `RA39`（`L205`）对 **`Radius/Scale` 施加单一合并规则（取 `max`）**；若为两个量，合并规则需分别定义 | 【原文】（**最强的结构性证据**） |
| **E-4** | `RA51`（`L232`）：`Extent` **必须由 `Radius/Scale` + 显式衰减形状标识 决定** → 该量是推导 `Extent` 的**单一输入** | 【原文】 |
| **E-5** | 同一量在其它处**只写 `Radius`**：`RA72` `L294`（紧支撑边界）、`RAV7` `L508`（合并合规）、附录 A `L600`；`Region_Design` `L230` 的来源量清单也只列 `Radius` | 【原文】 |
| **E-6** | `Region_Design` §4.1（`L274`）用 **`Size`** 表示"区域的影响尺度"，并括注"**半径 / 尺度参数**"；`RBD3`（`L496`）用 `Size` 作为紧支撑边界 | 【原文】 |
| **E-7** | **`Scale` 从未单独出现在任何定义句或独立条款中** | 【原文】 |
| **综合** | 上述 7 条一致指向"**一个量的多个名字**" | **【推断】**（**强推断，但非契约明文**） |

> **结论**：**有强证据倾向"同义/同量"，但没有明文声明**；因此不能把它写成"契约已冻结二者同义"。若设计者采纳该读法，应在契约中**明文登记**（§6 C2）。

### Q3：是否存在足够证据证明二者是**两个独立必需量**？

| 核查 | 结果 |
|---|---|
| 是否有条款**分别**约束 `Radius` 与 `Scale`？ | **无** |
| 是否有条款**分别**给出两者的合并/推导规则？ | **无**（`RA39` `L205` 只有一条 `max`；`RA51` `L232` 只有一条推导式） |
| 是否有条款同时要求两者都存在（"必需"）？ | **无**（§3.2 只给一行；`RA34`/`RA39`/`RA51` 只把它当一项） |
| 是否有来源规则同时产出两者？ | **无**（`Region_Design` `L230` 的来源量清单只列 `Radius`） |
| 对照：契约在"确实需要区分"时的写法 | `Epoch`/`Ordinal` 被**分别**写入 `RA9` 键（`L125`）与 `RA11` 约束（`L127`）→ 说明契约有能力、也习惯在需要时分开写 |
| **结论** | **不足以证明是两个独立必需量**（证据为**缺失型**：没有任何条款支持"两个"） |
